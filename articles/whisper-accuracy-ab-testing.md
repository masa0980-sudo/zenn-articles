Windows常駐の音声入力アプリ（[MO Voice](https://github.com/masa0980-sudo/mo-voice)）を個人開発しています。faster-whisper を使ったローカル完結型で、ホットキーを押して話すとカーソル位置にテキストが入るという、それだけのツールです。

作ってしばらく使っていると、当然ながら「もっと精度を上げたい」と思い始めます。特に技術用語です。「Claude Code」が「クロードコード」になる、「印字」が「インジン」になる。1日に何十回も使うので、地味に効いてきます。

そこで思いつく施策を片っ端から実装して、A/Bテストで効果を測りました。

**結果、5つのうち3つが棄却になりました。** しかも棄却されたのは、事前に「これは効くだろう」と最も期待していたものばかりでした。

この記事は、その**効かなかった記録**です。「Whisperの精度を上げる方法」の記事はたくさんありますが、「試したけどダメだった」を数値付きで書いた記事はあまり見かけないので、誰かの時間の節約になればと思います。

:::message
環境は CPU のみ（Core i7-8565U / 4コア8スレッド）、モデルは `small`、量子化 `int8` です。GPU があれば結論が変わる項目もあります。
:::

## 評価の土台をどう作ったか

施策の話に入る前に、評価基盤の話をさせてください。**ここが一番効きました。**

最初、私は精度改善を「体感」で判断していました。これは完全に失敗でした。修正を入れた直後は「良くなった気がする」となるのですが、翌日には分からなくなります。

そこで、こういう仕組みを入れました。

- 発話した音声を `data/audio/` に直近50件だけ保存する（リングバッファ）
- 認識結果を `history.jsonl` に、音声ファイル名付きで記録する
- ユーザーが `Ctrl+Alt+Z` で修正したら、その前後を `corrections_log.jsonl` に記録する

この3つを突き合わせると、**「音声ファイル」と「人間が直した正解テキスト」のペア**が自動で溜まっていきます。つまり、普通に使っているだけでテストセットが育つわけです。

評価は `difflib.SequenceMatcher` で一致率を出すだけの素朴なものです。

```python
from difflib import SequenceMatcher

def similarity(hypothesis: str, reference: str) -> float:
    return SequenceMatcher(None, hypothesis, reference).ratio()
```

WER（単語誤り率）のようなちゃんとした指標ではありませんが、日本語は単語境界が曖昧なので、文字ベースの一致率のほうが扱いやすいと判断しました。相対比較さえできれば十分です。

**この基盤を作ってから、以降の判断がすべて数値でできるようになりました。** 逆に言うと、これを作る前に試した施策は、正直あまり信用できません。

## 施策1: Obsidianのノートから語彙を学習させる ❌ 棄却

私は Obsidian に技術メモを大量に書いています。そこには「Claude Code」も「faster-whisper」も、私が普段使う固有名詞が全部入っています。

**これを Whisper の `initial_prompt` に渡せば、認識精度が上がるはずだ。**

そう考えて、vault をスキャンして頻出語を抽出し、prompt に注入する機能を作りました。実装としてはうまく動きました。3,238語が抽出され、上位の語が prompt に入りました。

そして実測しました。実発話11件、正解テキストは自分で修正したもの。

| 条件 | 平均一致率 | 差分 |
|---|---|---|
| **vault語彙なし** | **0.9019** | — |
| 語彙あり（絞り込みなし） | 0.8958 | -0.0061 |
| 語彙あり（英字スラッグを除外） | 0.8900 | -0.0118 |
| 語彙あり（英字語を全除外） | 0.8834 | -0.0185 |

**入れないほうが良い、という結果でした。**

しかも興味深いのは、「英字混じりの技術用語が悪さをしているのでは」という仮説で絞り込みを2通り試したところ、**絞るほど悪化した**ことです。

個別の変化を見ると、理由が分かりました。

改善した例:
- `クロードコード` → `Claude Code`
- `ファスターウィスパー` → `faster-whisper`

悪化した例:
- `印字` → `インジン`
- `機種` → `記者`
- `色々` → `いろいろ`

固有名詞は確かに改善します。しかし**普通の日本語が崩れる例のほうが数で上回る**のです。prompt に技術用語を並べると、モデルが「この文脈では技術用語が来るはずだ」と過剰に期待してしまう、という理解をしています。

### 教訓: 「書いてある語」と「話す語」は違う

振り返ると、前提が間違っていました。

**「ノートに書いてある = 発話される」という推測が成り立っていなかった**のです。技術メモに書く語（`_categories_for`、`ProseMirror`）と、口に出す語（「えーと」「これを」「あの機能」）は、思ったより重なりません。

対照的に、**ユーザーが実際に `Ctrl+Alt+Z` で修正した語**（corrections）は非常によく効きます。こちらは「実際に発話され、実際に誤認識された」という実績があるからです。

推測ベースの語彙と、実績ベースの語彙。この2つは区別すべきでした。

現在この機能は `use_vault_vocab: false` で**既定オフ**にしています。スキャン機能自体は将来 hotwords 方式に使えるかもしれないので残していますが、prompt への注入は止めました。

## 施策2: 読みが似ている語を自動で見つけて修正する ❌ 棄却

次に考えたのは、こういう仕組みです。

「クロードコード → Claude Code」という修正履歴があるなら、**読みが似ている別の誤認識も自動で見つけられるのでは？**

pykakasi で日本語をカタカナ読みに正規化し、`difflib` で類似箇所を探す実装を作りました。

```python
import pykakasi
kks = pykakasi.kakasi()

def to_kana(text: str) -> str:
    return "".join(item["kana"] for item in kks.convert(text))
```

既知の19ペアで検証したところ、**78.9%（15/19）を検出できました。** これは行けると思いました。

ところが、実運用を模した設定（41発話の中から「怪しい箇所」を探させる）で評価すると、**精度が25%まで落ちました。**

### なぜ落ちたのか

スコアの分布を見て、原因が分かりました。

```
誤検出: たいと→タイトル 0.86 / 進め→オススメ 0.86 / 今度→コマンド 0.86
正検出: 温泉→音声 0.75 / プログ→ブログ 0.67 / ロブ→ログ 0.50
```

**誤検出のほうがスコアが高いという逆転が起きています。** これでは閾値をどこに置いても分離できません。

根本的な原因は、「読みが似ている」ことと「実際に誤認識である」ことの相関が弱いことです。日本語には読みが似た正常な語が大量にあるので、当然といえば当然でした。

さらに厄介なのが、**英語表記に直したい語はスコアが0になる**ことです。

```
クロードコード → Claude Code   読み: クロードコード vs Claude Code → 0.00
コーデック    → Codec         読み: コーデック    vs Codec       → 0.00
```

pykakasi はアルファベットをカナに変換しないので、比較する土俵にすら乗りません。**技術記事の音声入力で一番直したいのは、まさにこの手の語**なのですが、読みベースの手法とは根本的に相性が悪いわけです。

### 教訓: 判別タスクと探索タスクは難易度がまったく違う

これが一番重要な学びでした。

- **判別タスク**: 既知のペア（wrong と right）が与えられ、その距離を測る
- **探索タスク**: wrong が未知の状態で、文中から怪しい箇所を探す

私が最初にやった78.9%の評価は**判別タスク**でした。答えが分かっている状態で「これは似ているか？」を判定していただけです。実際に必要だったのは**探索タスク**で、こちらは桁違いに難しい。

前者で良い数字が出ても、後者では使えません。

**この種の「自動検出」を検討するときは、必ず探索タスクの形式で実データ評価する。** これは今後も忘れないようにしたい教訓です。

なお、**読みの完全一致に限定した置換**（「クロードコードー」「クロード・コード」のような表記ゆれの回収）は採用しています。探索をやめて、既知パターンの正規化だけに絞れば安全に効きます。

## 施策3: 日本語特化モデルに置き換える ❌ 棄却

`kotoba-whisper-v2.0-faster` という日本語特化モデルがあります。「6.3倍速」と謳われていて、期待して試しました。

結果は**3.5倍遅い**でした。

| モデル | 20秒音声の認識時間 |
|---|---|
| faster-whisper `small` | 6.7秒 |
| kotoba-whisper-v2.0-faster | 23.3秒 |

「6.3倍速」は**GPU前提の数字**でした。CPU では逆に遅くなります。

速度だけならまだしも、品質面でも問題がありました。

- **句読点が全く出ない**（文がつながって読みにくい）
- 「解釈してして」のような重複
- 文節が丸ごと脱落することがある

一部の単語（「エージェント」「指示」）は確かに `small` より正確でした。しかし句読点が出ないのは、文章を書く用途では致命的です。

加えて、モデルのロードに50秒、ダウンロードに1.5GB。常駐アプリとしては重すぎます。

**ベンチマークの数字は前提条件を確認する。** 当たり前のことですが、実際に踏むと効きます。

## 施策4: 長い音声をVADで分割する ❌ 棄却

Whisper には「30秒ウィンドウ」の制約があります。`initial_prompt` は最初のウィンドウにしか効かないため、**30秒を超える発話では後半に語彙ヒントが効かない**という問題があります。

そこで、VAD（音声区間検出）で発話を分割し、**チャンクごとに `initial_prompt` を渡す**方式を試しました。

理屈は通っています。しかし実測すると：

| 条件 | 60秒音声の認識時間 |
|---|---|
| 分割なし | 15.3秒 |
| VADチャンク分割 | 26.9秒（**+76%**） |

事前に「+30%以内なら採用」という Go/No-Go 基準を決めていたので、これは大幅超過です。

さらに悪いことに、**品質も落ちました。**

- チャンク境界で文脈が切れ、「Claude Code」が「クロードコード」に退行
- 「AIがある。」のような、元の発話にない文の挿入

チャンクごとに独立して認識するため、文脈の連続性が失われるのが原因です。語彙ヒントを効かせるために文脈を犠牲にしていては本末転倒でした。

:::message
事前に Go/No-Go 基準を決めておいたのは正解でした。基準がないと「+76%だけど品質が上がったから…」と迷います。今回は品質も落ちたので即決でしたが。
:::

## 施策5: 単語レベルの信頼度でハイライトする ✅ 採用

ここでようやく採用された施策です。

faster-whisper は `word_timestamps=True` を指定すると、**単語ごとの信頼度**（`Word.probability`）を返してくれます。

```python
segments, info = model.transcribe(audio, word_timestamps=True)
for segment in segments:
    for word in segment.words:
        if word.probability < 0.6:
            # 怪しい語
            ...
```

コストは20秒の音声で+1秒程度。許容範囲です。

当初は「信頼度が低い語を自動で修正する」ことを考えましたが、これは施策2と同じ**探索タスク**なのでやめました。代わりに、**低信頼の語を黄色でハイライトして修正ダイアログを自動で開く**だけにしました。

判断は人間がします。精度が25%でも、**提示に留めれば実用になる**というのがポイントです。誤検出があっても「違うな」と思えば無視すればいいだけなので、コストがほぼゼロです。

### 実装上の注意: 1文字の語は除外する

閾値0.6未満をそのまま拾うと、**誤検出だらけになりました。**

原因は、セグメント先頭に現れる1文字の断片です。Whisper はセグメントの最初の語の確信度を低く出す傾向があり、「あ」「て」のような1文字が大量にヒットします。

**2文字以上に限定する**だけで、実用的な精度になりました。

## 施策6: トークナイザの特殊トークンを予算に計上していたバグ ✅ 採用

最後に、施策というよりバグ修正の話です。これは他の Whisper 実装でも踏む可能性があると思うので共有します。

`initial_prompt` には**224トークン**という上限があります。そこで私は、語彙を1つずつトークン化しながら予算内に収める実装をしていました。

```python
# バグのあるコード
def count_tokens(text: str) -> int:
    return len(tokenizer.encode(text).ids)

budget = 223
for term in terms:
    cost = count_tokens(term + "、")
    if used + cost > budget:
        break
    used += cost
```

一見問題なさそうですが、**Whisper のトークナイザは `encode()` のたびに制御用トークンを3個付けます**（`<|startoftranscript|>` など）。

```python
>>> len(tokenizer.encode("").ids)
3   # 空文字なのに3
```

つまり、語ごとに `encode()` を呼ぶと**毎回3トークンが余分に計上される**わけです。30語なら90トークン。**予算223の41%が、実在しないトークンで埋まっていました。**

実測すると、内部カウント219に対して、連結後の実コストは128でした。

修正は単純で、空文字のエンコード長を測っておいて差し引くだけです。

```python
_special_overhead = len(tokenizer.encode("").ids)   # → 3

def count_tokens(text: str) -> int:
    return max(0, len(tokenizer.encode(text).ids) - _special_overhead)
```

### 皮肉な話

このバグを直す前、`count_tokens()` は例外で落ちて概算（1文字≒1.1トークン）にフォールバックしていました。そして**その概算のほうが、偶然、実態に近かった**のです。

「正確なトークナイザに変えたら悪化した」という、なんとも言えない状況でした。

**トークナイザの `encode()` は特殊トークンを含むのが普通です。** 予算計算に使う前に、必ず `encode("")` の長さを測ってください。

## まとめ

| 施策 | 判定 | 理由 |
|---|---|---|
| Obsidian語彙をpromptに注入 | ❌ | 0.9019 → 0.8958 と悪化。書く語と話す語は違う |
| 読み類似での自動検出 | ❌ | 判別78.9%だが探索25%。誤検出のほうが高スコア |
| 日本語特化モデル | ❌ | CPUでは3.5倍遅い。句読点が出ない |
| VADチャンク分割 | ❌ | 時間+76%、かつ文脈が切れて品質も低下 |
| 単語信頼度でハイライト | ✅ | 提示に留めれば精度25%でも実用になる |
| 特殊トークンの控除 | ✅ | 予算の41%が無駄になっていたバグ |

改めて眺めると、**棄却された4つはすべて「推測で効きそうだと思ったもの」**でした。採用された2つは、実測とバグ修正です。

一番の収穫は、施策そのものより**評価基盤を先に作ったこと**でした。これがなければ、悪化した施策を「良くなった気がする」と思い込んだまま使い続けていたはずです。

そして施策2で得た「判別タスクと探索タスクは違う」という教訓は、音声認識に限らず使えると思っています。何かを自動検出する仕組みを考えるときは、**答えが分からない状態での評価**を必ずやる。これは今後も意識したいところです。
