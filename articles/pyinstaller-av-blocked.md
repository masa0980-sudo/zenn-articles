Windows常駐の音声入力アプリ（[MO Voice](https://github.com/masa0980-sudo/mo-voice)）を個人開発しています。faster-whisper を使ったローカル完結型で、ホットキーを押して話すとカーソル位置にテキストが入る、それだけのツールです。

これまではソース配布のみでした。導入手順が `git clone` → `python -m venv` → `pip install` の3ステップあり、Python を入れていない人には渡しづらい。そこで PyInstaller で exe 化することにしました。

**結論から言うと、exe は完成しました。起動10.2秒、メモリ425MB。ソース版と同等の性能です。それでも配布はやめました。**

理由は2つの躓きです。1つ目は自分のミスで直せました。2つ目は**お金を払わないと直らない**と分かりました。

この記事はその記録です。

:::message
環境は Windows 11 Home (10.0.26200) / Python 3.13 / PyInstaller 6.22.2 です。常駐しているウイルス対策ソフトはウイルスバスター クラウド（Windows Defender は無効）。
:::

## 前提：`--onefile` は最初から選ばなかった

PyInstaller には単一 exe にまとめる `--onefile` がありますが、これは使いませんでした。

`--onefile` は**起動のたびに中身を一時フォルダへ展開します**。このアプリは依存が重く、展開対象が300MB近くあります。ホットキーを押したらすぐ使えることが価値のツールで、起動に数十秒かかる作りにするわけにはいきません。

`--onedir`（フォルダごと配る形式）を選びました。結果的にこれは正解でしたが、後述するようにサイズの問題は残ります。

## 依存の多いアプリで PyInstaller が拾い切れないもの

まず spec を書く段階の話です。このアプリは DLL やデータファイルを持つパッケージが多く、素の `pyinstaller main.py` では動きませんでした。

```python
from PyInstaller.utils.hooks import collect_data_files, collect_dynamic_libs

datas = []
# faster-whisper は VAD 用の onnx モデルを同梱している。
# vad_filter=True で使うため、無いと録音のたびに実行時エラーになる
datas += collect_data_files("faster_whisper")
# pykakasi は読み仮名の辞書を .db として持つ
datas += collect_data_files("pykakasi")

binaries = []
binaries += collect_dynamic_libs("ctranslate2")
binaries += collect_dynamic_libs("onnxruntime")

hiddenimports = [
    # pynput はプラットフォーム実装を実行時に動的 import するため
    # 静的解析では拾えない
    "pynput.keyboard._win32",
    "pynput.mouse._win32",
    "win32gui", "win32process", "win32clipboard", "win32con",
]
```

特に **faster-whisper の VAD モデル（`silero_vad_v6.onnx`）** は忘れやすいところです。ビルドは通りますし起動もします。録音して認識しようとした瞬間に初めて落ちます。

逆に、明らかに使わない大物は `excludes` で削りました。PyQt5 は既定だと Qt の全モジュールが候補に入るので、`QtWebEngine` や `QtQml` などを外しています。

## 躓き1：起動途中で 0xC0000005 で落ちる

ビルドは通りました。実行すると、150MB ほど読み込んだところで無言で消えます。

```
ExitCode: -1073741819
```

`-1073741819` は `0xC0000005`、アクセス違反です。Python の例外ではないので、traceback は出ません。

### `console=False` にしていると何も見えない

常駐アプリなので `console=False`（ウィンドウアプリ）でビルドしていました。これだと**標準出力が繋がらないので、起動直後の例外が一切見えません**。

`console=True` にして作り直そうとしたのですが、これが後述する躓き2に阻まれて実行できませんでした。

### 答えは Windows のイベントログにあった

アクセス違反なら、Windows が「障害モジュール」を記録してくれます。

```powershell
Get-WinEvent -FilterHashtable @{LogName='Application'; StartTime=(Get-Date).AddMinutes(-20)} |
  Where-Object { $_.Message -match 'MOVoice' }
```

出てきたのがこれです。

```
Faulting application name: MOVoice.exe
Faulting module name: MSVCP140.dll, version: 14.26.28720.3
Exception code: 0xc0000005
Faulting module path: ...\_internal\PyQt5\Qt5\bin\MSVCP140.dll
```

**PyQt5 が同梱している Visual C++ ランタイムが原因でした。**

バンドルの中身を調べると、こうなっていました。

| 場所 | バージョン |
|---|---|
| `_internal\msvcp140.dll`（ルート） | 14.44.35211.0 |
| `_internal\PyQt5\Qt5\bin\MSVCP140.dll` | **14.26.28720.3** |
| システム（System32） | 14.44.35211.0 |

PyQt5 のホイールには2020年頃の古い CRT が入っています。一方 ctranslate2 や onnxruntime は新しい CRT を前提にビルドされている。**古い方が先に読み込まれ、新しい版の関数を呼んだ時点でクラッシュする**という構図でした。

### 対処：古い方だけを落とす

spec で、PyQt5 に同梱された CRT だけをバンドルから除外します。ルートにある新しい版（無ければシステムの再頒布可能パッケージ）が使われるようになります。

```python
_OLD_CRT = {
    "msvcp140.dll", "msvcp140_1.dll", "msvcp140_2.dll",
    "vcruntime140.dll", "vcruntime140_1.dll", "concrt140.dll",
}


def _is_pyqt_bundled_crt(entry):
    dest = str(entry[0]).replace("/", "\\").lower()
    return dest.rsplit("\\", 1)[-1] in _OLD_CRT and "pyqt5" in dest


a.binaries = [e for e in a.binaries if not _is_pyqt_bundled_crt(e)]
```

これで4本（`MSVCP140` / `MSVCP140_1` / `VCRUNTIME140` / `VCRUNTIME140_1`）が除外され、**クラッシュは解消しました**。

起動10.2秒、メモリ425MB。ソース版（約10秒・412MB）とほぼ同じです。exe 化としては成功でした。

## 躓き2：ウイルス対策ソフトが実行させてくれない

こちらが本題です。

ビルドした exe を実行しようとすると、こう返ってきます。

```
Program 'MOVoice.exe' failed to run: Access is denied
```

同時にウイルスバスターが「**不審なファイルのブロック**」というダイアログを出します。「このファイルは安全でない可能性があります。信頼できる提供元からのファイルのみ開いてください」という文言です。

### 切り分け：コードは無関係だった

最初は「依存が多くて怪しく見えるのだろう」と考えました。そこで対照実験をしました。

```python
print("hello from pyinstaller")
```

**この1行だけの exe をビルドして実行したら、同じようにブロックされました。**

| 検証 | 結果 |
|---|---|
| MO Voice の exe（314MB・依存多数） | ブロック |
| **`print` 1行だけの exe** | **ブロック** |

コードも依存関係も無関係です。**PyInstaller で作った署名なし exe である**ことが理由でした。

### スキャンの除外設定は効かない

「除外フォルダに登録すればいい」と考えるところですが、これが効きませんでした。ただし、ここで私は一度**誤った結論の出し方**をしています。

最初に試したとき、私は除外フォルダの**外**（`%TEMP%`）に置いた exe がブロックされたことを根拠に「除外は別系統だから効かない」と判断しました。**これは対照実験になっていません。** 除外していない場所のファイルが止まるのは当たり前です。

正しくやり直しました。

1. 除外がレジストリに実際に登録されているか確認する
2. 除外フォルダの**内側**に置いて実行する
3. **ウイルス対策ソフトを再起動してから**実行する

3番目が重要でした。常駐プロセスが起動時に例外リストを読み込んでキャッシュしている可能性があり、これを潰さないと「効かない」とは言えません。

結果はこうです。

| 検証 | 結果 |
|---|---|
| 除外がレジストリに登録されているか | ✅ 登録済み |
| 除外フォルダの内側で実行 | ❌ ブロック |
| 製品を再起動してから実行 | ❌ ブロック |
| 別名コピー（新規ファイル扱い）で実行 | ❌ ブロック |

レジストリを見ると、例外リストは `Scan\Exceptions` の一か所しかありませんでした。機能別のキーは多数あるのに、この「不審なファイルのブロック」機能用の除外リストは存在しません。

つまり**スキャンの除外設定とは別系統の判定**で、こちらには除外が効かないということです。最初の直感は合っていたのですが、根拠の出し方が間違っていました。

### 決定的だったのは「再ビルドで再発する」こと

途中で一度、`MOVoice.exe` が実行できるようになりました。ところが**同じ設定でビルドし直した瞬間、また止まりました。**

これで性質が確定しました。パターンマッチではなく**評価（レピュテーション）ベースの判定**です。「署名がなく、実績のない実行ファイル」を止めている。だからファイルが変われば、中身が同じでも再び未知のファイルになります。

## なぜ配布をやめたか

ここまでで、こういう状況だと分かりました。

- 手元では、ダイアログで許可すれば動く
- **受け取った人の環境でも同じダイアログが出る**
- しかも**更新のたびに再発する**（新しいバイナリは毎回「未知のファイル」）

日本ではウイルスバスターの利用者が多く、無視できる割合ではありません。そして表示が「不審なファイル」「安全でない可能性があります」なので、**そもそも実行してもらえません**。「ちょっと便利なツール」を配るのに、この第一印象は致命的です。

誤検知報告という手もありますが、これは署名検出ではなく評価ベースなので、報告が通ってもビルドし直せば元に戻る可能性が高い。根本的な解決になりません。

根本的な解決はコード署名証明書です。OV 証明書で年3〜5万円、EV 証明書なら年8万円〜。EV なら即座に信頼されます。

**まだ誰も使っていないツールに、年数万円を先払いする段階ではない**と判断しました。ダウンロード数が見えてから考えます。

## 残したもの

ビルド一式（spec・バッチ・8サイズ入りアイコン）はリポジトリに残してあります。証明書を導入したら、バッチを叩くだけで配布へ移れる状態です。

そして README からは exe のダウンロード導線を**消しました**。存在しない Releases を案内するわけにはいきませんし、「配布していない理由」は `packaging/README.md` に検証結果ごと書いてあります。

## サイズの話（おまけ）

配布サイズは **314MB** でした。内訳の上位はこうです。

| パッケージ | サイズ |
|---|---|
| PyQt5 | 75MB |
| av.libs（PyAV） | 63MB |
| ctranslate2 | 60MB |
| onnxruntime | 34MB |
| numpy.libs | 21MB |

音声モデル（約500MB）は含んでいません。初回起動時にダウンロードする作りなので、これは配布物に入れていません。

それでも314MBです。`--onedir` を選んでいるので起動は速いのですが、「ちょっと試す」には重い。仮に署名の問題が解決しても、このサイズは別の課題として残ります。

## まとめ

| 躓き | 原因 | 解決 |
|---|---|---|
| 起動途中に 0xC0000005 | PyQt5 同梱の古い CRT が先に読まれる | spec で除外して解決 |
| 実行が Access denied | 署名なし exe への評価ベースの判定 | **お金（コード署名）が必要** |

技術的な問題はイベントログを見れば解けました。**イベントログの「障害モジュール」は、`console=False` で何も見えない状況での最後の手がかり**になります。ここは覚えておく価値があります。

一方で、2つ目は技術で解ける問題ではありませんでした。個人開発で Windows 向けに exe を配るなら、**コード署名のコストを最初から見込んでおく**必要があります。「PyInstaller で固めれば配れる」とはいかない、というのが今回の実感です。

もうひとつ持ち帰ったのは、切り分けの作法です。「除外の外にあるファイルが止まった」を根拠に結論を出しかけたのは、単純に実験として雑でした。**除外が効かないと判断する前に、「登録されているか」「再起動したか」「除外パスの内側で試したか」を潰す。** 当たり前のようで、答えが見えた気になっていると飛ばしてしまうところです。
