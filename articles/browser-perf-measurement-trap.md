ブラウザで動く自作のシューティングゲーム [NEON VOID](https://masa0980-sudo.github.io/neon-void/)（敵の弾を避けながら進むゲーム）を個人開発しています。全5面あり、面ごとに違うBGM（背景で流れる音楽）が流れます。音源ファイルは使わず、すべてブラウザ上で合成しています。

ある日、自分でプレイしていて気づきました。3面あたりからBGMが途切れ、5面では止まります。

音が途切れるのだから、原因は音の処理にある。そう考えるのが自然です。私もそうしました。

**しかし犯人は描画でした。しかも私は、そこに辿り着くまでに推測で4回直しています。**

さらに悪いことに、その4回のあいだ、私は自分の測定環境で症状が再現していないことに気づいていませんでした。AIに測らせていた環境は、1コマも絵を描いていなかったのです。

この記事はその記録です。

:::message
環境は Windows 11 と Chrome（ブラウザ）です。ゲームは単一のHTMLファイルで、Canvas（ブラウザ上に絵を描く仕組み）へ毎フレーム描画しています。測定に使ったのは Claude Code の Browser pane、claude-in-chrome、Playwright の3つです（どれもブラウザを自動で動かす手段）。
:::

## 症状：3面から途切れ、5面で止まる

BGMは面ごとにテンポが違います。1面は148、2面は88、そして5面は176BPM（1分あたりの拍数）です。

テンポが上がるほど、1秒あたりに鳴らす音は増えます。症状も面が進むほど悪化しました。

そこで私は「音の処理が重くて間に合っていない」と考えました。この見立て自体は間違っていません。実際、音の作り方には無駄がたくさんありました。

ただ、それは主因ではありませんでした。

## 最初にやるべきだったのは「その環境は本当に描画しているか」の確認

私は測定をAIに任せていました。長時間プレイさせて、音のずれを記録させる。そういう進め方です。

返ってくる答えは、いつも「異常なし」でした。

この時点で疑うべきでした。ユーザー（私自身）は再現できているのに、測定側では一度も再現しない。これは症状の情報ではなく、測定環境の情報です。

### 3秒間に1コマしか描かれていなかった

確認はこれだけで済みます。

```js
// これが 0 に近ければ、描画は1コマも走っていない
window.__f = 0;
(function p(){ window.__f++; requestAnimationFrame(p); })();
// 3秒待ってから window.__f を読む
```

`requestAnimationFrame` は、ブラウザが1コマ描くたびに呼び返してくれる関数です。毎秒60コマ（60fps）なら、3秒で約180回になるはずです。

実測は**3秒間に1回**でした。

ログ上のfpsは0。`setInterval` も1秒に1回以下まで抑えられていました。

つまりゲームのループが1コマも走っていません。主スレッド（ブラウザが処理を順にこなす1本の流れ）は常に暇です。その裏で、音声だけが理想的な条件で動きます。

ここで何時間走らせても「異常なし」しか出ません。

### 測定環境3種の可否

| 環境 | 描画 | 用途 |
|---|---|---|
| Browser pane | ❌ 非表示だと停止 | 動作の確認のみ |
| claude-in-chrome | ❌ 背面のタブでは停止 | 実質使えない |
| Playwright | ✅ 実際に描画される | 描画の測定はこれ一択 |

Browser pane も claude-in-chrome も、画面に映っていないと描画が止まります。ブラウザの省電力の仕組みなので、正しい挙動です。

問題は、止まっていることが結果に出ない点です。fpsは「0」ではなく、そもそも記録されません。

描画を測るなら Playwright の headless（画面を出さずにブラウザを動かすやり方）を使います。名前に反して、こちらは実際にラスタライズ（描画命令を実際の点に変換する処理）まで行います。

```python
# 描画性能はこの形でしか測れなかった
pg.evaluate("window.__fps=[];")
pg.wait_for_timeout(4000)
r = pg.evaluate("({avg: ..., worst: ...})")
pg.screenshot(path="out.png")   # 見た目が壊れていないかも必ず確認する
```

### CPUを遅くする機能も効かなかった

もうひとつ回り道をしました。CDP（Chrome DevTools Protocol、ブラウザを外から操作する仕組み）には、CPUをわざと遅くする機能があります。

これで負荷を再現しようとしました。しかし**10倍遅くしても音のずれは出ません**でした。

このスロットリング（速度をわざと落とす機能）は主スレッドにしか効きません。音声は別のスレッドで動くので、影響を受けなかったのです。

## 推測で直した4回

再現できないまま、私は思いつく順に直していきました。

| # | 直したもの | 結果 |
|---|---|---|
| 1 | 音の予約処理の作り直し | 改善するが再発 |
| 2 | 止まったBGMの自動復帰 | 別症状の対症療法 |
| 3 | 音質の手動切替を追加 | 判断を利用者に丸投げ |
| 4 | 画面に診断表示を出す | ← これが当たり |

1〜3は、どれも「効きそう」と思って入れたものです。実際に多少は効きました。だから余計に、原因を突き止めた気になれてしまいます。

4回目でようやく方針を変えました。直すのをやめて、実機の数値をもらうことにしたのです。

## Canvasの関数単位の計測は当てにならない

回り道の途中で、もうひとつ誤診をしています。

描画の中で何が重いかを調べようと、関数を `performance.now()` で挟んで測りました。結果、HUD（画面上の得点や残機の表示）を描く関数が**1フレームの57パーセント**を占めていました。

ここを削れば直る。そう考えて手を入れました。

あとで同じ関数だけを取り出して測り直すと、**0.15ms**しかありませんでした。57%は誤りです。

Canvasは描画命令をその場で実行しません。命令を溜めておき、あとでまとめて点に変換します。関数を時間で挟む測り方は、そのコストを別の場所に付け替えて報告してしまいます。

非表示のペインではもっとおかしな結果も出ました。光の表現を**切ったほうが遅い**のです。命令が実行されておらず、記録するだけの時間を測っていたためでした。

Canvasの性能は、端から端までのfpsで測るしかありません。内訳は当てにしないほうが安全です。

## 実機に診断表示を出したら一発で分かった

4回目の修正で、F2キーで開く診断表示を入れました。出す値は、詰まっている層を切り分けられるものに絞ります。

```
音声追従 1.00  （最悪 0.36）
拍/秒    9.9
fps      37  （最低 37）
例外     0
音量     0.280   音軽量 OFF
```

これをユーザー（私）に見てもらい、数値だけを報告してもらいます。返ってきた値で、原因はその場で確定しました。

- 例外は**0件**。発音処理は失敗していない
- 音声追従の最悪値は**0.36**。音は実時間の3分の1しか進んでいない
- そして**ポーズ中でもfpsが37**しかない

### ポーズ中のfpsが決め手だった

ポーズ中は敵も弾も動きません。ゲームのロジック（敵や弾を動かす処理）は止まり、描画だけが走っています。

そこでfpsが37ということは、1コマに27msかかっている計算です。60fpsに必要なのは16msですから、描画だけで予算を使い切っています。

主スレッドが描画で埋まると、音を予約する処理が順番を待たされます。その結果としてBGMが途切れていました。

**ポーズ中のfpsは、描画かロジックかを切り分ける強い手がかりです。** ここが落ちていれば、原因は描画で確定します。

### 診断の数値は計測条件を限定する

この診断表示でも一度、読み間違えています。

最初はポーズ中の値も記録していました。そこで音声追従が落ちるのを見て、「音声側の処理落ちだ」と判断したのです。

実際は違いました。音を出していないとき、Chromeは音声の処理を休ませます。休んでいるものを「遅れている」と読んでいただけでした。

いまは「プレイ中かつ再生中」に限って記録し、それ以外は測っていない旨を画面に出しています。

## 描画を直したあと、音声側で効いた5つ

描画を軽くしたことで症状は解消しました。ただし音の作り方の無駄も、実際に測ると相当なものでした。効果が大きかった順に挙げます。

**1. サンプリングレート（1秒間に音を何回刻むかの値）が96kHzだった。** 48kHzの倍の処理量を払っていました。この曲は大半が8kHz以下なので、上限を抑えるだけで負荷が半分になります。

```js
let baseRate=48000;
try{ const probe=new AC(); baseRate=probe.sampleRate; probe.close(); }catch(e){}
// 弱い端末は 24kHz。DSP（音の信号処理）の量はレートに正比例するため丸ごと半減する
const target = WEAK_DEVICE ? 24000 : Math.min(baseRate,48000);
try{ ac = new AC({latencyHint:0.04, sampleRate:target}); }
catch(e){
  try{ ac = new AC({latencyHint:0.04}); }
  catch(e2){ ac = new AC(); }   // 未対応のブラウザは従来どおり
}
```

`latencyHint` は、音を出すまでの遅れをどれくらい許すかの希望値です。40msを指定するとバッファ（貯めておく余裕）が増え、1回の処理が間に合わなくても途切れにくくなります。

**2. スケジューラ（音を先に予約していく処理）が、遅れを取り戻そうとして自滅していた。**

```js
/* 遅れた分の音符を一度に予約すると、過去時刻の音が同時に鳴って団子になる。
   しかもノードが一気に数百個生まれて音声側をさらに圧迫し、
   「詰まる→まとめ予約→もっと詰まる」の悪循環になる。
   大きく遅れたら追いつくのを諦め、現在時刻へ飛ばして拍を取り直す。 */
if(nextStepTime < now - 0.05){
  const skip=Math.ceil((now-nextStepTime)/stepDur);
  currentStep+=skip;
  nextStepTime+=skip*stepDur;
}
```

先読みの長さも足りませんでした。0.12秒では、画像の読み込みや面の切り替えで簡単に足が出ます。0.6秒まで伸ばしています。

**3. ノイズ音を毎回作り直していた。** ハイハット（打楽器の音のひとつ）や爆発音のたびに領域を確保し、乱数で埋めていました。実測で10秒あたり220回、乱数は84万回です。

```js
function noiseSource(t,dur){
  if(!NOISE_BUF){                          // 2秒分を1回だけ作る
    const len=Math.floor(ac.sampleRate*2);
    NOISE_BUF=ac.createBuffer(1,len,ac.sampleRate);
    const d=NOISE_BUF.getChannelData(0);
    for(let i=0;i<len;i++) d[i]=Math.random()*2-1;
  }
  const n=ac.createBufferSource();
  n.buffer=NOISE_BUF;
  const room=Math.max(0,NOISE_BUF.duration-dur-0.02);
  n.start(t, Math.random()*room, dur+0.02);   // 毎回ちがう位置を切り出す
  return n;
}
```

確保が220回から1回になりました。ここはGC（使い終わった領域の自動回収）が頻発し、主スレッドを止めていた箇所です。

**4. フィルター（特定の高さの音を削る部品）を音ごとに作っていた。** 設定が固定なら面ごとに1つで足ります。

コツは「音量の変化→フィルター」の順にすることです。フィルターは線形なので、順序を入れ替えても音は変わりません。この順なら音量の変化だけが音ごとに独立するので、フィルターを共有できます。毎秒306個から219個まで減りました。

**5. 鳴り終わったあと、部品を切り離していなかった。** 実測で毎秒207個が繋がったまま残り、無音を処理し続けていました。

```js
function cleanupAfter(src,nodes){
  if(!src) return;
  src.onended=()=>{ for(const n of nodes){ try{ n.disconnect(); }catch(e){} } };
}
```

## try/catchの握りつぶしは「正常に見える無音」を作る

音を1つ鳴らし損ねただけで予約処理全体が止まると、以後ずっと無音になります。だから例外は握る必要があります。

ただし握りつぶしたままにすると、最悪の状態が生まれます。**処理は動いているのに毎回失敗していて無音**、という状態です。

これは健康チェックの上では完全に正常に見えます。例外は出ず、ループも回っているからです。

対処は単純で、件数と内容を必ず数えて診断表示に出すことです。今回は「例外0件」と分かったからこそ、音声側の疑いを外して描画に絞れました。

もうひとつ、設定の持たせ方でも危ないことをしました。3回目の修正で音質の手動切替を入れ、選択を `localStorage` に保存していたのです。

自動判定に一本化したときにUIを消したのですが、保存値はそのまま残ります。**軽量に固定されたまま、二度と戻らない**状態になるところでした。

```js
/* 以前の選択が残っていると「手動指定」とみなされ自動判定が働かない。
   UIを外すときは保存値も消しておく。 */
try{
  localStorage.removeItem('neonVoidAudio');
  localStorage.removeItem('neonVoidFx');
}catch(e){}
```

いまは手動の切替を持たず、fpsを見て自動で落とします。

```js
// 50を3秒下回ったら光を切る。58以上が20秒続けば戻す（往復を防ぐため差をつける）
if(fps<50){ fpsFastRuns=0; if(++fpsSlowRuns>=3) lowFX=true; }
else if(fps>=58){ fpsSlowRuns=0; if(lowFX && ++fpsFastRuns>=20){ lowFX=false; fpsFastRuns=0; } }
```

## まとめ

| 誤診 | 実際 |
|---|---|
| 測定環境で異常なし | 1コマも描画していなかった |
| HUDの描画が57% | 単独で測れば0.15ms |
| 音声側の処理落ち | ポーズ中でも37fps。描画が主因 |
| 音を出していない間の遅れ | Chromeが処理を休ませていただけ |

やらないほうがよかったことを、5つに畳んでおきます。

- 再現できていない環境の「異常なし」を根拠に、直ったと判断する
- Canvasの関数単位の計測を根拠に、削る場所を決める
- 診断の数値を、計測条件を確かめずに読む
- 例外を握りつぶしたまま放置する
- 利用者の作業中のタブを奪って測定する

一番の教訓は最初の1行です。**症状が再現しない環境で測った結果は、良い知らせではありません。** 何も分からなかった、というだけです。

推測で4回直した時間より、実機の数値を1回もらった時間のほうが、はるかに短く済みました。次に同じ場面が来たら、直す前に診断表示を入れます。
